# Deploying the demo — GitHub Pages and GitLab Pages

The published artefact is a static directory, `_site/`, produced by
`node scripts/build-demo.mjs`:

```
_site/
  index.html          landing page
  vanilla/            framework-free viewer
  react/              React demo (bundle regenerated by examples/build-react.mjs)
  dist/               the library: index.js document.js loader.js mount.js
                      remote.js worker.js text.js styles.css index.d.ts
                      react/ wasm/pdf-reader.{mjs,wasm}
  reader-sample.pdf   the fixture the demos open
```

Everything inside `_site/` is written with **relative** URLs, so the same
directory works at `/`, at `/<project>/` (GitHub and GitLab project pages), and
behind any reverse proxy. Nothing in it needs a server: there is no route
handling, no CORS, no headers to set beyond `application/wasm` (which the static
hosts already send).

Two things are easy to get wrong:

- **`dist/wasm/pdf-reader.wasm` must be present.** It is committed, but if you
  rebuild the wasm and forget to commit it, the deployed page still loads the old
  binary from the host cache.
- **`dist/worker.js` + `dist/remote.js` must be present.** Worker mode (the
  default in both demos) fetches `worker.js` at runtime; a missing file falls
  back to the inline path silently unless you check `viewer.document.mode`.

## GitHub Pages (current)

Two branches: `main` holds the source, `gh-pages` holds `_site/`.

> **There is no Pages workflow, on purpose.** `.github/workflows/pages.yml` used
> `actions/deploy-pages`, and this repository's Pages *source* is the `gh-pages`
> branch, so every push to `main` failed with `Invalid deployment branch and no
> branch protection rules set in the environment. Deployments are only allowed
> from gh-pages`. Two coherent setups exist; this repo uses the branch, because
> the deploy is two commands and needs no settings:
>
> - *branch deploy (current)*: no workflow, `cp -r _site/. /tmp/ghpages/` +
>   push, which is what the recipe below does;
> - *Actions deploy*: restore a workflow with `upload-pages-artifact` +
>   `deploy-pages`, and switch Settings → Pages → Source to **GitHub Actions**.
>   Do not do both — the branch push and the workflow overwrite each other.

```bash
git push origin main

node examples/build-react.mjs      # committed-ish artefact, gitignored: rebuild
node scripts/build-demo.mjs        # -> _site/

# a reusable worktree for gh-pages
git worktree add /tmp/ghpages gh-pages 2>/dev/null || true
cp -r _site/. /tmp/ghpages/

git -C /tmp/ghpages add dist index.html react vanilla reader-sample.pdf .nojekyll
git -C /tmp/ghpages commit -m "deploy: <what changed>"
git -C /tmp/ghpages push
```

Verify what the server actually returns. GitHub Pages serves the previous file
from cache for up to a minute, so always cache-bust:

```bash
curl -s "https://dionaditya.github.io/wasm-pdf-reader/dist/wasm/pdf-reader.wasm?v=$RANDOM" | sha256sum
sha256sum dist/wasm/pdf-reader.wasm
```

For a JS-only change the wasm hash cannot catch a missed deploy — compare
`dist/mount.js`, `dist/document.js`, `dist/worker.js` and `dist/styles.css` too.

## Migrating to GitLab

The repo is a plain git repository with no GitHub-specific machinery: the only
thing tied to GitHub is the `gh-pages` branch and the Pages URL. GitLab Pages
builds from CI instead, so `gh-pages` stops being needed.

### 1. Create the project

GitLab → **New project → Create blank project**. Name it `wasm-pdf-reader`,
namespace = your user or group, **uncheck** "Initialize repository with a
README" (the history already exists). Visibility: public, if the Pages site
should be public (with a private project, Pages needs GitLab access control
switched on, and every viewer then needs a GitLab account).

### 2. Add the remote and push

```bash
cd ~/wasm-pdf-reader
git remote add gitlab git@gitlab.com:<namespace>/wasm-pdf-reader.git
git push -u gitlab main
```

Branch protection, MR approvals, issue trackers — all optional, none of them
needed for Pages.

### 3. Add the Pages pipeline

`.gitlab-ci.yml` is committed and does exactly this:

1. `unit` — `npm ci` + `node test/unit.mjs` (needs no compiler: `dist/` ships).
2. `pages` — `npm ci`, rebuild `examples/react/bundle.js`, run
   `scripts/build-demo.mjs`, move `_site/` to `public/`, assert the three files
   the page fetches at runtime exist, publish `public/` as the Pages artifact.

`public` is the only path GitLab Pages serves; the job publishes on the default
branch only, so merge requests just run the tests.

### 4. Wait for the pipeline, then verify

CI/CD → Pipelines → the `pages` job → **Pages** in Deploy → URL is
`https://<namespace>.gitlab.io/wasm-pdf-reader/`. Then:

```bash
curl -s "https://<namespace>.gitlab.io/wasm-pdf-reader/dist/wasm/pdf-reader.wasm?v=$RANDOM" | sha256sum
sha256sum dist/wasm/pdf-reader.wasm
curl -sI "https://<namespace>.gitlab.io/wasm-pdf-reader/dist/worker.js"   # 200, text/javascript
```

Open `/vanilla/` and `/react/` and check `viewer.document.mode === 'worker'` in
the console: a 404 on `worker.js` degrades to the inline path and looks like a
slow-but-working demo.

Known GitLab Pages behaviours to expect:

- The first deployment can take a few minutes; later ones are seconds.
- **Unique domain** (Settings → Pages) is on by default for new projects — the
  site is then `https://<namespace>-<random>.gitlab.io/wasm-pdf-reader/`. The
  relative URLs make that harmless; turn it off if you want the stable
  `namespace.gitlab.io` host.
- A custom domain goes in Settings → Pages → New domain, DNS `CNAME` to
  `<namespace>.gitlab.io`.

### 5. Run both hosts while you decide

Both publish the same static tree; keeping both costs one extra command per
deploy. To push every commit to both remotes:

```bash
git remote set-url --add --push origin git@github.com:dionaditya/wasm-pdf-reader.git
git remote set-url --add --push origin git@gitlab.com:<namespace>/wasm-pdf-reader.git
git remote -v      # origin listed twice = push to both
git push origin main
```

`gh-pages` is not mirrored by that (it is a separate branch), so keep the
`cp -r _site/. /tmp/ghpages/` step if the GitHub URL must stay current.

The alternative is GitLab's pull mirroring (Settings → Repository → Mirroring
repositories, needs a GitHub personal access token). It only works one way per
repository, so pushing to both remotes is simpler for a repo of this size.

### 6. Retiring GitHub

Only after the GitLab URL is verified:

1. `README.md` — the demo links, `repository`, `homepage` in `package.json`, and
   the badge/CI references (search for `github.com/dionaditya` and
   `dionaditya.github.io`).
2. `CLAUDE.md` §7 (the deploy recipe) — replace the `gh-pages` steps with the
   pipeline.
3. GitHub repo → Settings → **Transfer** (or Archive). GitHub keeps a redirect
   for the old URL; `gh-pages` can be deleted.
4. `npm publish` is unaffected — npm reads `package.json`, not the host.

## What must never be deployed

`test/fixtures/` contains deliberately broken and encrypted PDFs; only
`reader-sample.pdf` is published, on purpose. The C++ sources, `scripts/` and
`node_modules/` stay out of `_site/`. `build-demo.mjs` copies an allow-list, not
the repo — keep it that way.
