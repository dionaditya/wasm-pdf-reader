# Roadmap — from "reads most PDFs" to MuPDF-grade output

Last verified: 2026-10-27 (wasm 3.1 MB, 1.9 MB gzipped; 76 unit checks; 20 e2e
steps; 10 ranged steps; 2 Pages demos). Capability parity against pdf.js 6.4.299 /
MuPDF.js 1.28.1: **77 % / 81 %**
weighted, regenerated with `node scripts/competitive-parity.mjs` (the README table
is that script's output — do not hand-edit it). Working notes for an agent doing
this work: `CLAUDE.md`.

MuPDF is both the target and the oracle: every claim below is measured against it
with `~/pdfvenv/bin/python` + `pymupdf` at `Matrix(1,1)`, comparing ink ratio and
mean absolute channel difference. Do not add a feature to this list without a
fixture that fails today.

## Strategy

1. **Fixture first.** One PDF per feature, generated by a committed script
   (`scripts/make_*.py`) from a real producer where possible. Hand-written
   minimal PDFs for filters; real files (pdf.js corpus, pdfium test data) for
   anything a generator would get wrong. The generated PDF is what gets
   committed, not the 9 MB font or the source image.
2. **Numeric gate before the commit.** Render with `node test/render-to-png.mjs`,
   diff against MuPDF, and only then look at the picture. Numbers say *where*,
   vision says *what*.
3. **One feature, one commit, one README line.** The README capability list and
   the "not supported" paragraph are part of the deliverable — they drift within
   a week otherwise.
4. **Unit check per feature, in `test/unit.mjs`.** Assert pixels (counts, ink in
   a region, colour presence) and API output, never "it rendered".
5. **e2e stays green.** `test/e2e.mjs` covers both demos, the text layer and the
   per-page pixel baseline. Refresh the baseline only for an intended change,
   and say so in the commit.
6. **Ship the same day.** `./build.sh && npm run build:js && node test/unit.mjs
   && node test/e2e.mjs`, then push `main`, rebuild `_site`, push `gh-pages`,
   and sha256-compare the served wasm against local. A deploy is not done until
   the hashes match.
7. **Budget the wasm.** 3.1 MB today; keep the ceiling at 4 MB. lcms2 (~400 KB)
   and a full openjpeg port (~1 MB) both fit if nothing else grows.

## Milestones, in order

### M1 — ICC colour management (3–4 days) — *partial: parser + images, fills still table-driven*
*Why*: every print-derived PDF is CMYK or carries an ICC profile; today the raw
values are painted, so colour is visibly off next to MuPDF. Biggest visible win
per day of work.
*Where*: `src/cpp/pdfraster.cpp` — `cmykToRgb()` (line ~601), the settings that
carry `fill`/`stroke` (`GState`), `drawImage` colour conversion, and the `cs`/`CS`
operators that currently ignore `colorspaces` (`(void)colorspaces`, line ~1636).
*Approach*: compile lcms2 to wasm, create a transform per `/ICCBased` stream
(and the built-in SWOP/FOGRA fallbacks for `/DeviceCMYK`), cache transforms on
the object number, convert 3/4-component input to the sRGB output profile.
Keep the fast path (no profile, gray/RGB) untouched.
*Fixture*: one page per source profile — CMYK print PDF, a tagged sRGB-rgb PDF,
`/ICCBased` N=4, `/CalRGB`.
*Accept*: ≤ 2/255 mean abs diff on the CMYK page (MuPDF is colour-managed);
untagged pages unchanged within 0.2/255.
*Risk*: transform setup cost per page — cache per profile, not per pixel.

### M2 — Tiling patterns (1–2 days) — *done*
*Why*: table backgrounds, watermarks, hatch fills, chart fills. Absent today;
the operator simply does nothing.
*Where*: `pdfraster.cpp` — `setColorSpace`/`scn` handling (~line 1610), and a new
`paintTilingPattern()` next to `paintShading()` (~line 1009). The interpreter
already has `Do` and `q`/`Q`, which a pattern is: a matrix, a BBox, an XStep/YStep
and a content stream.
*Approach*: on `scn` with a name and `/PatternType 1`, paint the tile into a
scratch `Canvas`, then blit with the pattern matrix × CTM, clipping to the current
path. Handle `/PatternType 2` by routing to `paintShading`. Cache the rendered
tile per (object, scale) — PDFs stamp the same tile thousands of times.
*Fixture*: a page with a two-colour checker tile at 45°, a hatch fill under text,
and a pattern used as a text fill colour.
*Accept*: ≤ 2/255 mean abs diff; no seams at tile boundaries.
*Risk*: unbounded tile sizes — clamp the tile bitmap allocation like a page.

*Landed*: `paintTilingPattern()` renders the cell once per (pattern, scale) into
a transparent buffer at 3× device resolution and samples it through the inverse
of `/Matrix × CTM`, so rotation and skew need no special case; PatternType 2
routes to the shading painter clipped to the path. Two bugs worth remembering:
`Mat::mul(X)` applies *this first* (composing the tile offset the other way
painted every cell outside its own buffer), and averaging texel colour without
premultiplying drags tile edges towards black. Remaining gap: the 45° checker
sits at 7.65/255 — the geometry is right and the ink matches within 1%, so what
is left is edge quality, not placement. Try sampling with bilinear weights or
rendering the cell at 4× and box-filtering.

### M3 — Blend modes and transparency groups (~1 week) — *done, minus `/SMask`*
*Why*: logos, shadows, overlapping highlights and any `/Group /Transparency` form.
Today only `/ca` alpha exists, so composited artwork looks flat or too dark.
*Where*: `GState` (~line 582) gains `/BM`, `/ca`, `/CA`, `/AIS`, `/SMask`;
`Canvas::blend` (~line 36) gains the blend functions; form and page rendering
(~line 1101) needs an offscreen `Canvas` when the group is non-isolated.
*Approach*: render the group to its own buffer, then composite with the blend
function and group alpha; implement the separable modes (Multiply, Screen,
Overlay, Darken, Lighten, ColourDodge, ColourBurn, HardLight, SoftLight,
Difference, Exclusion) and the non-separable four (Hue, Saturation, Colour,
Luminosity). Keep `Normal` on the direct path.
*Fixture*: a page with a Multiply-logo over a photo, a group with `/ca 0.5`, and
one page per non-separable mode.
*Accept*: ≤ 3/255 on the photo composite; no darkening where alpha is 1.
*Risk*: memory — a group buffer per nested form. Cap the nesting depth (say 8)
and fall back to direct painting with a warning.

### M4 — Mesh shadings 4–7 and shading type 1 (3–5 days) — *partial: 4/5 landed, 1/6/7 open*
*Why*: gradient-heavy marketing PDFs, charts, and background artwork.
*Where*: `Interp::paintShading` (~line 1009), which currently rejects anything
that is not type 2/3.
*Approach*: type 1 is `ShadingFn` per pixel — reuse the existing function
evaluator. Types 4–7 are triangle meshes: decode the stream (bits per coordinate
/component, `/Decode` ranges), then Gouraud-fill each triangle (type 4/5) with
affine colour interpolation; types 6/7 patch meshes need a Coons/tensor patch
subdivision — start with a fixed 4×4 subdivision and check the seam.
*Fixture*: a type 4 mesh, a type 5 (lattice) mesh, a type 6 Coons patch, and a
type 1 function shading.
*Accept*: ≤ 3/255 mean abs diff per page; banding-free on a smooth gradient.
*Risk*: type 7 is the long tail — ship 1/4/5/6 first, warn on 7.

*Landed*: `paintMeshShading()` decodes `/BitsPerCoordinate`,
`/BitsPerComponent` and `/Decode` and Gouraud-fills triangles with 2×2
subpixel coverage; `scripts/make_shading_fixture.py` writes `mesh.pdf` (one
type 4 page, one type 5 lattice). Two defects keep the milestone open:
1. **Type 4 does not read the per-vertex edge flag** that §8.7.4.5.5 requires
   (`readVertex(tri[i], false, flag)`), and the fixture omits it as well, so the
   fixture is malformed — MuPDF correctly paints nothing on page 1 while we
   paint a gradient. Fix the fixture and the reader together; the current
   "match" proves nothing.
2. **Type 5 disagrees with MuPDF by 87/255** on page 2: our render folds the
   lattice into two large triangles instead of connecting the 2×2 cells, so the
   vertex ordering is wrong, not just the edge quality (ink 0.69 vs 0.96).
Types 1 (function shading), 6 (Coons) and 7 (tensor) still warn and paint
nothing. Do not describe mesh shadings as supported in the README until both
numbers are inside the gate.

### M5 — Separation / DeviceN and tint transforms (2 days) — *done*
*Why*: spot colours (brand inks, meterai-style stamps) currently collapse into a
component guess, so they render black or wrong.
*Where*: `pdfraster.cpp`, the colour-space resolution used by `sc`/`scn`,
`drawImage` and shadings (three copies of the same switch today — factor it into
one `colorSpaceFrom()` helper as part of this).
*Approach*: `/Separation` = 1 tint → `/TintTransform` (type 2 or 4 function) →
alternate space; `/DeviceN` = n tints → same. Then colour-manage through M1.
*Fixture*: a Separation page (spot red 50 %), a DeviceN with 2 inks, and a
`/Lab` fill.
*Accept*: ≤ 2/255 with the alternate space being CMYK; the spot renders as its
alternate, not as black.
*Risk*: postscript-function types 0 and 4 — reuse `ShadingFn::eval`, extend it.

### M6 — JPEG 2000 decoder (3–5 days) — *open*
*Why*: **broken today** — OpenJPEG-produced codestreams decode to noise while
MuPDF is correct. This is the only item where the output is garbage rather than
merely less accurate.
*Where*: `src/cpp/jpx-decoder.cc` (2070 lines, vendored from nanopdf).
*Approach*: first write a native probe that dumps SIZ/COD/QCD/SOT tile-part
geometry and the decoded DC level for `test/fixtures/photo-jpx.pdf`; the failure
smells like tile-part/layer handling rather than entropy decode, since a flat
colour image is also wrong. If the port is structurally off, vendor openjpeg's
`j2k` decoder (BSD-2) the way JBIG2 was vendored, rather than repairing it.
*Fixture*: `photo-jpx.pdf` (synthetic chart, committed) plus one photo-encoded
JP2 and one raw `.j2c` codestream.
*Accept*: ≤ 4/255 mean abs diff against MuPDF on all three; no garbage page.
*Risk*: size — a full openjpeg port costs ~1 MB wasm. Check the budget first.

### M7 — Type3, Type1 PFB, CID-CFF in OpenType (~1 week) — *Type3 and OTTO done, PFB open*
*Why*: old TeX/plot output (Type3), legacy Type1 (PFB), and CJK OTFs whose CFF
sits inside an `OTTO` wrapper currently come out as substitute faces — plausible
but wrong glyphs.
*Where*: `pdfdoc.cpp` font loading (~line 1544, `/FontFile`, `/FontFile3`,
`/CharProcs`), `pdfraster.cpp` `showText` (~line 744) for the Type3 path.
*Approach*: Type3 = a content stream per glyph in glyph space, painted with the
text matrix — reuse the form-XObject interpreter with a `/CharProcs` lookup and
`/FontMatrix`. PFB = strip the segment headers, then feed the Type1 charstrings
to the existing Type2 interpreter (they share the format family). CID-CFF in
OpenType = parse `CFF ` table out of the sfnt and hand it to `CffFont`.
*Fixture*: one page each, from a real producer — check the pdf.js corpus
(`test/pdfs`) for a Type3 sample; `cid_cff.pdf` is already a fixture.
*Accept*: ≤ 1/255 on text pages; glyph count from `getPageText` unchanged.
*Risk*: Type3 `/ImageMask` glyphs and `/ColorSpace` in the glyph dict.

### M8 — OCG, widgets, forms (2 weeks) — *done*
*Why*: layer toggling and fillable forms are what makes a reader feel complete;
MuPDF generates widget appearances and fills AcroForm state.
*Where*: new `pdfocg.cpp` + `pdfform.cpp`; `pdfraster.cpp` annotation loop
(~line 1974) for visibility and appearance generation; JS viewer layer for the
panel and the field model.
*Approach*: honour `/OCProperties` `/D` visibility (and `/VE` for the UI);
generate `/AP` for widgets that lack one (border, background, value, font); expose
`getForm()`/`setField()` on the document and let the viewer write `/V` in a copy.
*Fixtures*: an OCG file with two layers, a 4-field AcroForm (text, checkbox,
radio, choice).
*Accept*: hidden layers paint nothing; a filled field renders as filled text and
survives a re-render at another scale.
*Risk*: scope creep into scripting — do not implement `/AA` JavaScript.

### M9 — Architecture — *M9.1 + M9.2 done, M9.3 half done (cache yes, display list no)*
*Why*: it is the last structural gap and the biggest single score gain on the
comparison table (+3.0 points, the difference between "toy on a 200-page scan" and
"replacement"). It is also the only item that cannot be bolted on later: the
parser's `read(offset,len)` boundary and the display list both change how the
renderer is called.

Sub-items, in this order — each ships independently and leaves the tests green:

**M9.1 — Web Worker for parse + render (3–4 days) — *done*.**
*Where*: new `src/js/worker.js` (the worker entry) + a `WorkerPool` in
`src/js/document.js`; `mount.js` and `src/js/react/hooks.js` switch to the pool
behind an option (`worker: true`), synchronous path stays the default until M9.3.
*Approach*: one module instantiation per worker (the module owns a single bitmap,
so one worker can serve one render at a time); post the file bytes once, then
`{op:'render', page, scale, dpr}`; transfer the RGBA `ArrayBuffer` back and
`putImageData` on the main thread. Text/links stay request/response JSON. Fall
back to the inline path when `Worker` is unavailable.
*Accept*: no long task > 50 ms on the main thread while scrolling 20 pages at
fit-width; both demos load with `worker: true`; e2e green with one new step
asserting the worker path is actually taken (not silently falling back).
*Risk*: the wasm heap is per worker, so N workers = N heaps (each up to 1 GiB
reserved, 64 MB pre-grown for JBIG2). Start with one worker; cap the pool at
`navigator.hardwareConcurrency - 1` only after measuring.

*Landed*: `src/js/worker.js` (the worker entry, one module per worker, one queue
because the module owns a single bitmap) + `src/js/remote.js` (`PdfRemoteDocument`
and a `WorkerPool` that one worker serves until its last document closes).
`PdfDocument.open(src, {worker: true})` returns the remote document, which keeps
the *synchronous* part of the API by capturing geometry, metadata, outline, form
fields and warnings once at open time; text and links ride back on the render
response (warmed cache, so the viewer's existing `getText`/`getLinks` calls keep
working) and `search()`/`getPageText()` are Promises. `{worker: 'strict'}` throws
instead of falling back, and a fallback records why on `document.workerError` —
silent fallback was the risk the acceptance line was written against.
Accept measured in `test/e2e.mjs`: a scale-3/dpr-2 render takes ~900 ms of worker
time while a 2 ms timer on the main thread fires ~200 times (the inline path
fires it 0 times), `document.Module` is undefined on the main thread, and a
round trip for a page that was never rendered returns its text runs.
Both demos run worker mode; the e2e pixel baseline is unchanged, which is the
point (same rasterizer, different thread).

Two things this exposed, both fixed in the same change:
- **A fallback must be loud.** The first cut fell back silently when the worker
  404'd (the React demo's bundle resolves `workerUrl` against the page, not the
  library), and every "worker" assertion passed while nothing was threaded.
- **Cyclic structure in the file.** `Document::outlineJson()` recursed without a
  visited set, so `/First` pointing at its own item looped forever (it hung, it
  did not crash: the wasm stack has no guard page), and the page-tree walks in
  the parser, the outline's page index and the form builder re-descended into
  cyclic `/Kids`, inflating a 1-page file to 40 pages. Same class as
  CVE-2025-46206 (mupdf `strip_outline`). Fixed with visited sets + depth/item
  caps; `test/fixtures/outline-cycle.pdf` and three unit checks hold it down.

**M9.2 — Ranged loading (1–2 weeks, parser work) — *done*.**
*Where*: `pdfdoc.cpp` byte access (every `read`/`memcpy` of the source buffer),
`src/js/document.js` `copyIntoWasm`, and a `fetch` wrapper that issues `Range`
requests.
*Approach*: put `read(offset, len)` behind the parser and page the file in on
demand (4–64 KB chunks, LRU on the JS side); use `Range: bytes=` when the origin
supports it, otherwise a full fetch. This is the only way past the 1 GiB
whole-file ceiling and the reason a 300 MB scan currently cannot open on a phone.
*Fixture*: a > 100 MB synthetic scan (`scripts/make_large_fixture.py`), plus a
server that answers 206 and one that does not (both paths must work).
*Accept*: 100 MB document renders page 1 while < 10 MB has been fetched; peak
wasm heap < 150 MB; `test/unit.mjs` still passes with a `read`-instrumented
source that fails on any access beyond the fetched window.
*Risk*: encryption and linearised files read non-sequentially — the encrypted
path must not assume the whole buffer is resident. Keep the monolithic path as a
fallback for `< 16 MB`.

*Landed*: `src/cpp/pdfsource.hpp` (`ByteSource` + `MemorySource` +
`CallbackSource`), `pdfdoc.cpp` reads through it, and `Document::Lex` became an
offset-tracking lexer that slides a window instead of assuming one contiguous
buffer. The resident path (`direct()`) is the pre-M9.2 behaviour with no copies,
so every existing test still exercises the same code; `windowBytes` forces a
window even for an in-memory file, and `test/unit.mjs` parses 14 fixtures
through a **2 KB** window asserting identical page count, page-1 pixels and text
— that is what proves the lexer surgery rather than a lucky fixture.

Measured on the generated 117 MB / 240-page fixture (`scripts/make_large_fixture.py`,
`npm run test:ranged`): opening, rendering page 1, page 240 and extracting text
fetched **5.37 MB of 117 MB in 260 range requests**, peak wasm heap **16 MB**
(acceptance: < 10 MB fetched, < 150 MB heap). A server that ignores `Range` and
answers 200 is survived by keeping the first full body and slicing it locally.

*Routing (added with the rotation commit)*: the ranged path is no longer opt-in
when it is the only one that can work. `PdfDocument.open` refuses an inline copy
above **512 MB** (half the 1 GiB ceiling, because a render needs headroom) before
growing anything, and routes the source through worker + ranged loading even when
`{ worker: true }` was not passed. That needs a sliceable source (`File`/`Blob` or
a URL) — a bare `ArrayBuffer` above the budget still fails with the copy error.
"Too large to copy" and "the heap could not grow past N MB" are separate errors,
each naming the real numbers, so a desktop failure no longer reports as a mobile
memory cap. Measured in Chromium: a **1031 MB** / 240-page file opens ranged in
**1.8 s**, 8.8 MB fetched, 16 MB heap.
`close()` also clears the per-worker range fetch hook, or the second big document
threw and silently fell back to a whole-file copy.

Two things this cost that are worth remembering:
- **Window granularity is the whole ballgame.** A fixed 1 MB window fetched
  82 MB of the same file, because reading 240 page dicts is 240 random jumps and
  each jump paid 1 MB. The window now starts at 16 KB, doubles while access is
  sequential (up to 1 MB) and drops back on a jump: same fixture, 5.37 MB.
- **The worker's page-geometry snapshot walks every page.** That is what the
  random jumps *are*, and it is also why opening a 240-page ranged document
  takes ~3 s over HTTP (260 sync XHRs). Batching the page-tree read is the
  obvious next optimisation; it is not a correctness issue.

**M9.3 — Display list + page cache with a budget (1 week) — *page cache done,
display list open*.**
*Where*: `pdfraster.cpp` gains a record/replay split (interpret once into a
display list, rasterize that), `src/js` gains a byte-budgeted LRU of page bitmaps.
*Approach*: pair each display list with the scale it was recorded at; replay at
the requested scale where possible, re-record only on font/CTM changes that
matter. Budget the cache in bytes (`navigator.deviceMemory`-derived default,
overridable) and evict least-recently-used, never the visible page.
*Accept*: scrolling a 200-page document ahead and back does not grow the heap
beyond the plateau measured by `test/memory.mjs`; re-layout (zoom) on a cached
page < 30 ms; pixel hashes unchanged at the same scale.
*Risk*: display lists encode the CTM at record time; text and shadings recorded
at one scale can look wrong replayed at another. Restrict replay to
translation-only changes first and re-record otherwise — a wrong fast path is
worse than a slow correct one.

*Landed (cache half)*: `src/js/page-cache.js` — a byte-budgeted LRU of rendered
page bitmaps on both document kinds, default budget from
`navigator.deviceMemory` (8–96 MB), `pageCacheBytes` to override, `pageCache:
false` to disable, `document.pinPage()` so the visible page survives eviction.
Accept: a repeat render at a cached scale is a bitmap copy — `test/e2e.mjs`
measures it at a few milliseconds (gate: < 30 ms) and the pixel baseline is
unchanged, because the cache returns the same bytes the renderer produced.
`test/ranged.mjs` sweeps 60 pages of the 117 MB fixture forward and back inside
a 16 MB budget and asserts the cache never exceeds it and the wasm heap stays
under 150 MB. Two bugs it introduced and fixed: the worker must **not** cache
(every reply transfers the RGBA buffer, so a cached copy would be detached by the
next request), and `setField()` must invalidate the page or a refill is invisible
(that trap is already the first item in CLAUDE.md's forms notes).

*Not landed*: the display list itself. A cached scale is fast; a **new** scale
still interprets the content stream from scratch, which is the 30 ms line above
only for pages already cached. Doing it properly means splitting
`pdfraster.cpp`'s interpreter from its rasterizer and deciding what may be
replayed at a different CTM — text (glyph bitmaps), shadings (colour ramp
sampling) and patterns (tile scale) each break differently. That is a week of
work with a strong chance of a subtly wrong fast path, so it is priced and left
open rather than rushed.

Already landed, and not part of the above: `document.outline`,
`document.metadata`, the page rail's lazily rendered thumbnails, a print action
that rasterizes every page, and **90° view rotation** (⟲ / ⟳ in both toolbars,
`setRotation` / `rotateLeft` / `rotateRight` / `rotation` on the viewer
controller, `defaultRotation` and `onRotationChange` in React). Rotation is a
view transform, not a re-render: the page box swaps for 90°/270° and the layer
holding canvas + text + links + highlights turns onto it, so overlays stay
hit-testable and the pixel hashes do not move. The known residue is in *Known
smaller defects* (a page whose own `/Rotate` is non-zero compounds with a rotated
view in the text layer). Probed by e2e ("viewer capability probes return booleans,
not undefined" and "the toolbar turns the view and swaps the page box").

## Non-goals

Do not budget these to "match MuPDF"; they are a different product:

- **Text shaping (HarfBuzz)**. MuPDF does not shape PDF text either — it paints
  the glyphs the file names. The real bug is narrower: when we substitute a face
  for an unembedded font we cannot lay out Arabic/Indic. Fix that with a
  "no shaped fallback, warn" path, not a shaper.
- **Writing**: incremental updates, redaction, signing, PDF creation.
- **Other input formats**: XPS, EPUB/CBZ, SVG, the HTML/CSS (Story) engine.
- **OCR** (Tesseract) and document JS (`/AA`, MuJS) beyond form-field rendering.
- **Public-key encryption** (`/Adobe.PubSec`) — vanishingly rare in the wild.

## Compliance items

- **Rename the embedded font subsets' internal `name` tables** (`fonts_data.h`,
  families 3-7: Liberation/Carlito carry Reserved Font Names, and a subset is a
  Modified Version under OFL-1.1). Matching happens on the PDF's `/BaseFont`
  string and the faces are addressed by key (`sans_regular`, …), so the rename is
  mechanical: rewrite the `name` table of each byte array to `Wpdf Sans` /
  `Wpdf Serif` / `Wpdf Mono` / `Wpdf Carlito` / `Wpdf Caladea`, regenerate the
  header, re-run the render diffs. Do not lose the copyright lines in
  `THIRD-PARTY.md` when doing it.
- Re-check `LICENSES/` when a vendored component is replaced; the OFL and
  Bitstream-Vera texts are committed there because the fonts ship inside the wasm.

## Known smaller defects (fix opportunistically)

- A rotated *view* (`rotation` / the ⟲ ⟳ buttons) turns the whole layer, so a
  page whose own `/Rotate` is non-zero and which also has a text layer compounds
  two rotations; the text layer offset for an intrinsically rotated page is the
  older, separate gap.
- Text layer emits the raw code for a font with an embedded CMap and no
  `/ToUnicode` (page 3 of `cjk-cmaps.pdf` extracts "A" for 日). Emit nothing, or
  the CID, rather than a plausible wrong letter.
- Password must be supplied to `open()`; PDF.js asks mid-parse. Add an
  `onPassword` callback that retries, ~half a day.
- `getPageText` is run-based; PDF.js users expect line/block structure. Grouping
  already exists in `src/js/text.js` (`groupLines`) — expose it as an option.
